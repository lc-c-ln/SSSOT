# [PRD] 로컬 Ollama 기반 IT 서비스 요청 처리 및 소스·문서 자동화 시스템

| 항목 | 내용 |
|---|---|
| 문서 상태 | Draft v0.4 (확정 결정 5건 + D3 수정) |
| 작성일 | 2026-10-14 (v0.2~v0.3: 2026-10-15) |
| 기준 저장소 | `lc-c-ln/sssot` (기존 `ssot` 문서 동기화 도구를 확장) |

---

## 1. 개요

### 1.1 목적
외부 연동 없이 **로컬 Ollama LLM**으로 IT 서비스 요청(SR)을 수신하고, 관련 소스 분석 → 수정안(Diff) 제안 → 담당자 승인 후 커밋 → 문서 자동 갱신 → 데이터 수정 시 DB 테이블 영향 분석까지 수행하는 **온프레미스 자동화 플랫폼**을 만든다.

### 1.2 배경 및 핵심 방침
- **보안**: 소스·문서·DB 정보가 외부 클라우드로 나가지 않는다. LLM은 로컬 Ollama만 사용한다.
- **휴먼 에러/지연 방지**: 반복적인 소스 분석, 데이터 수정 대상 테이블 추적, 문서 갱신을 자동화한다.
- **문서 동기화 지속성**: 소스 커밋이 발생하면 관련 문서를 즉시 최신 상태로 맞춘다.

### 1.3 설계 원칙 (모든 기능에 적용)
1. **사람이 최종 결정한다.** LLM은 제안만 하고, 코드 반영·SQL 실행·문서 적용은 승인 없이 일어나지 않는다.
2. **SQL은 절대 자동 실행하지 않는다.** 검증용 SELECT / UPDATE 안만 제시한다.
3. **LLM 출력은 코드가 검증한다.** (예: 문서 패치의 "올바른 값"이 소스에 실제 존재하는지, Diff가 `git apply --check`를 통과하는지)
4. **원본 비파괴.** 문서는 `*.updated.*` 또는 별도 브랜치로 저장하고, 삭제는 알림만 한다. (기존 SSSOT 원칙 유지)
5. **폐쇄망 동작.** 런타임에 인터넷 접속이 필요 없다.

## 2. 범위

### 2.0 확정된 결정 사항
| # | 결정 | 영향 |
|---|---|---|
| D1 | 대상 언어는 **Java / Spring**만 (v1) | 기존 `java_analyzer`·`facts`를 영향도 분석의 기반으로 사용. 타 언어는 범위 밖 |
| D2 | Git 호스트는 **GitLab** (사내 설치형) | 승인 시 브랜치 push + **Merge Request** 생성, 커밋 감지는 GitLab Webhook(Push Event) 사용 |
| D3 | DB 스키마 출처는 **① 별도 제공 문서(기본)** + **② 실제 DB 메타데이터 조회(선택, 환경별 설정)** | 접속 불가 환경은 문서만으로 동작. 접속 가능 환경은 메타데이터를 읽어 문서와 대조. 어느 쪽이든 SQL 자동 실행은 없음 |
| D4 | DB는 **Oracle (AWS RDS for Oracle)** | 생성 SQL은 Oracle 방언 고정(아래 R-21a). RDS는 관리형이므로 DBA 전용 구문·`SYS` 객체는 제안 대상에서 제외 |
| D5 | SR 입력은 **자체 웹 폼만** (v1) | 외부 티켓 시스템 연동 불필요. `POST /api/sr`는 유지하되 내부용 |

### 2.1 대상 자산
| 구분 | 설명 |
|---|---|
| 로컬 Ollama LLM | 온프레미스 서버의 LLM 실행 환경 (CodeLlama, Llama-3, DeepSeek-Coder, Qwen 등) |
| 소스 | Git/로컬 저장소의 프로젝트 소스 |
| 문서 | Markdown, docx, xlsx, 로컬 Wiki, API 명세서, DB 테이블 정의서 |
| IT 서비스 요청(SR) | 기능 개선, 버그 수정, 데이터 수정 등 요청 티켓 |

### 2.2 범위 밖 (Non-Goals)
- 외부 SaaS 티켓 시스템(Jira 등) 직접 연동 (v1은 자체 SR 등록 + REST 수신 API만)
- DB에 대한 SQL **자동 실행**
- Java/Spring 외 언어 지원 (D1)
- 원격/클라우드 LLM 사용 (기존 OpenAI·Claude 어댑터는 이 제품 모드에서 비활성화)
- 다중 테넌트, SSO (v1은 로컬 계정 기반)

## 3. 사용자 및 시나리오

| 역할 | 하는 일 |
|---|---|
| 요청자 | SR 등록, 진행 상태 조회 |
| 담당자(승인자) | Diff 검토 → 승인 / 수정 요구 / 반려, 데이터 수정 SQL 안 확인 |
| 관리자 | 모델·저장소·DB 스키마 소스 등록, 감사 로그 조회 |

**S1. 소스 수정 SR**: 요청 등록 → Ollama가 "소스 수정 건"으로 분류 → 영향 파일/함수 탐색 → Diff 생성 → 담당자 승인 → 브랜치 커밋 → 문서 패치 제안 → 문서 승인 → 반영.

**S2. 데이터 수정 SR**: 요청 등록 → "데이터 수정 건"으로 분류 → 관련 테이블/컬럼 식별 → 영향 범위(FK·연관 테이블) + 검증 SELECT / UPDATE 안 제시 → 담당자가 복사해 직접 실행.

**S3. 외부 커밋 감지**: SR과 무관하게 개발자가 커밋 → Git Hook이 감지 → 문서 패치 제안 생성.

## 4. 시스템 구성

```
[ SR 등록 (웹/REST) ]
        │
        ▼
[ Orchestrator (로컬 서버) ] ──REST──> [ 로컬 Ollama ]
        │   ├─ 분류 (소스/데이터)          (생성 모델 + 임베딩 모델 bge-m3)
        │   ├─ 검색 (Local RAG: 벡터 + AST/Grep)
        │   ├─ Diff 생성 / 검증
        │   ├─ 문서 패치 생성 / 검증
        │   └─ 스키마 매핑
        ▼
[ Git 저장소 ]   [ Vector DB ]   [ 문서 저장소 ]   [ 로컬 DB (SR·감사로그) ]
```

- 권장 구현: Python 3.11+, 가능한 한 표준 라이브러리 유지. 선택 의존성은 **오프라인 설치 가능**해야 한다(wheel 사전 반입).
- Vector DB: 1순위 ChromaDB(또는 FAISS) 임베디드 모드, 불가 시 AST/Grep 인덱스만으로 degraded 동작.
- 로컬 DB: SQLite (SR, 승인, 감사 로그).

## 5. 기능 요건

### 5.1 SR 수신 및 분류 (F-00, F-01)
- **R-1** SR 등록 필드: 제목, 본문, 요청자, 대상 저장소/시스템, 첨부(선택). 웹 폼과 `POST /api/sr` 제공.
- **R-2** Ollama 호출 클라이언트(`/api/generate`, `/api/chat`, `/api/embeddings`): 타임아웃, 재시도, 모델명 설정, 스트리밍 옵션, `temperature=0` 기본.
- **R-3** 분류 결과는 JSON 스키마 `{type: "code"|"data"|"unknown", confidence, reason}` 로 강제하고, 파싱 실패/`unknown`/낮은 신뢰도는 **담당자 수동 분류**로 넘긴다.
- **R-4** 담당자는 분류를 변경할 수 있고, 변경 이력은 감사 로그에 남는다.

### 5.2 코드베이스 인덱싱 및 영향도 분석 (F-02)
- **R-5** 소스·문서를 청크로 분할해 로컬 임베딩 모델(bge-m3 등)로 Vector DB에 저장. 증분 갱신(변경 파일만).
- **R-6** 하이브리드 검색: 벡터 유사도 + 기존 `java_analyzer`의 구조 정보(클래스/메서드/매핑 경로)·Grep 결합.
- **R-7** 영향도 결과는 "파일 · 클래스/함수 · 선정 근거(점수/매칭 키워드)" 목록으로 표시하고, 담당자가 대상 파일을 추가/제외할 수 있다.

### 5.3 소스 수정안 및 승인 워크플로우 (F-03)
- **R-8** 코드 특화 모델이 수정안을 **unified diff + 수정 이유**로 생성. 컨텍스트 윈도우 초과 시 파일/함수 단위로 분할 처리.
- **R-9** 생성된 Diff는 대상 저장소에 대해 `git apply --check`로 사전 검증. 실패 시 1회 자동 재생성 후에도 실패하면 "생성 실패"로 표시(승인 불가).
- **R-10** 웹 Dashboard에서 수정 전/후 Diff 비교, 수정 이유, 영향 파일 표시. 액션: **승인 / 수정 요구(코멘트 → 재생성) / 반려(사유 필수)**.
- **R-11** 승인 시: 작업 브랜치(`sr/<id>-<slug>`) 생성 → Diff 적용 → 커밋(메시지에 SR ID, 승인자 포함) → GitLab에 push → **Merge Request 자동 생성**(설명에 SR 링크·수정 이유·영향 파일). **기본 브랜치 직접 푸시는 하지 않는다.** GitLab 접근은 프로젝트 Access Token(최소 권한: `write_repository`, `api`)을 사용하며 토큰은 설정 파일/환경변수로만 보관하고 로그에 남기지 않는다. MR 머지는 GitLab의 기존 리뷰 절차에 맡긴다(시스템이 머지하지 않음).
- **R-12** 승인자는 요청자와 다른 사람이어야 한다(설정으로 해제 가능).

### 5.4 커밋 연동 문서 자동 갱신 (F-04)
- **R-13** 커밋 감지: **GitLab Webhook(Push Event)** 을 `POST /api/hooks/gitlab`로 수신(Secret Token 헤더 검증 필수). 기본 브랜치로 머지된 커밋을 문서 갱신 대상으로 하되, SR 브랜치 push도 선택적으로 처리. 5.3의 승인 커밋과 외부 커밋 모두 동일 경로로 처리. Webhook 수신이 불가한 환경을 위해 `ssot sync-commit <sha>` CLI와 로컬 Git Hook 스크립트도 보조로 제공.
- **R-14** 1단계(규칙 기반): 기존 SSSOT 엔진으로 표(컴포넌트·API·설정)를 소스와 대조해 변경 항목 산출. LLM 없이 동작.
- **R-15** 2단계(LLM): 커밋 Diff와 관련 문서 구간을 Ollama에 전달해 "틀린 값 → 올바른 값" 형태의 패치 제안 생성. 올바른 값이 소스·Diff에 존재하지 않으면 폐기(기존 검증 로직 재사용).
- **R-16** 문서 패치는 항목별 승인 후 반영(기존 웹 UI 승인 흐름 재사용). 사람이 쓴 설명은 덮어쓰지 않는다.
- **R-17** 대상 포맷: md, docx, xlsx 우선(구현 완료). 로컬 Wiki 연동은 v2 검토.

### 5.5 데이터 수정 요청 및 테이블 영향 분석 (F-05)
- **R-18** 스키마 소스 수집: **별도 제공되는 DB Schema 문서**(테이블 정의서 md/xlsx/docx 및 DDL 파일 가정)를 파싱해 테이블·컬럼·타입·PK/FK·설명을 구조화하고 로컬에 캐시. 문서 갱신 시 재수집. ORM 매핑 코드(JPA `@Entity/@Table/@Column`, MyBatis XML)는 스키마 문서와의 **불일치 경고용 보조 출처**로만 사용. **실 DB 접속은 선택 기능(R-18a)이며 기본은 꺼짐.** 스키마 문서의 정확한 형식은 샘플 수령 후 파서 규격을 확정한다(열린 질문 참조).
- **R-18a** 실 DB 메타데이터 조회(선택, 설정으로 활성화): Oracle RDS에 **읽기 전용 전용 계정**으로 접속해 딕셔너리 뷰(`ALL_TAB_COLUMNS`, `ALL_CONSTRAINTS`, `ALL_CONS_COLUMNS`, `ALL_INDEXES`, `ALL_COL_COMMENTS` 등)만 조회한다. 규칙:
  - 업무 테이블의 **데이터 행은 조회하지 않는다**(기본). 건수 확인 등 데이터 조회가 필요하면 별도 옵션으로 분리하고 담당자 승인 + 감사 로그 + 읽기 전용 + 타임아웃/행 제한을 적용한다(열린 질문 참조).
  - 접속 정보(호스트·서비스명·계정·비밀번호)는 설정 파일/환경변수/시크릿 파일로만 보관, 로그·프롬프트에 포함하지 않는다.
  - 접속 계정에는 `SELECT_CATALOG` 수준 또는 대상 스키마 `SELECT` 외 권한을 부여하지 않는다(DML/DDL 권한 없음). 시스템이 임의 SQL을 DB로 보내는 경로는 만들지 않는다.
  - 스키마 문서와 DB가 다르면 **불일치 리포트**(테이블/컬럼 누락·타입 차이)를 담당자에게 보여주고, 기본 우선순위는 실 DB > 문서(설정 변경 가능).
  - Oracle 드라이버(python-oracledb Thin 모드, 선택 의존성)는 폐쇄망 반입용 wheel로 제공. 미설치/미접속 시 문서 모드로 자동 대체.
- **R-19** 스키마 RAG: 자연어 요청 → 관련 테이블/컬럼 후보 + 근거 출처(파일:라인) 출력.
- **R-20** 영향 범위: FK·참조·ORM 연관 관계에서 연관 테이블 목록 도출.
- **R-21** 산출물: 검증용 `SELECT`(영향 건수 확인) 와 `UPDATE` 안, 롤백/백업 권고 문구. 모든 SQL에 **"자동 실행되지 않음"** 표시. `UPDATE/DELETE`에 `WHERE` 없는 안은 생성 후 코드가 차단한다.
- **R-21a** Oracle 방언 규칙: 식별자 대소문자(미인용 시 대문자) 처리, 행 제한은 `FETCH FIRST n ROWS ONLY`(또는 `ROWNUM`), 날짜는 `TO_DATE/TO_TIMESTAMP`, 문자열 연결 `||`, 빈 문자열=NULL 주의, 시퀀스 `NEXTVAL`. `UPDATE/DELETE` 안에는 영향 건수 확인용 `SELECT COUNT(*)`를 쌍으로 제시하고 "`COMMIT`은 담당자가 확인 후 직접 수행" 문구를 붙인다. `DROP/TRUNCATE/ALTER`, `SYS/SYSTEM` 스키마 대상, `WHERE` 없는 변경 문은 생성 후 코드가 차단한다.
- **R-22** 존재하지 않는 테이블/컬럼을 참조하는 SQL은 스키마와 대조해 경고한다. (DB 접속 모드에서는 `EXPLAIN PLAN` 등 DB 측 검증을 쓰지 않는다 — 실행 계획 생성도 DB에 SQL을 보내는 행위이므로 v1 제외.)

### 5.6 감사 로깅
- **R-23** 로컬 DB에 기록: Ollama 요청/응답 전문(모델명·파라미터 포함), SR 상태 변경, 분류 변경, 승인자·승인 시각·사유, 커밋 해시, 문서 수정 이력(전/후).
- **R-24** 로그는 수정/삭제 불가 방식(append-only, 해시 체인 선택)으로 저장하고, 웹에서 SR 단위 조회·CSV 내보내기 제공.
- **R-25** 프롬프트에 비밀정보(키·비밀번호 패턴)가 있으면 마스킹 후 저장하는 옵션.

## 6. 비기능 요건

| 구분 | 요건 | 검증 방법 |
